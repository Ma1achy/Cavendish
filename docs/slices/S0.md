`docs/research/s0-app-stack-and-build-speed.md`. Look and interaction: `docs/viewer-mockup/` and

## 1. What the owner can newly do

- **Open the app** (`cargo run -p cav-app`) and see the room and the five towers in a 3-D view, with the
  menu bar, the outliner, the properties panel, the per-tower timeline, the console and the footer.
- **Look around**: orbit, pan and zoom; perspective or orthographic; the named views (iso, top, bottom,
  north, south, east, west) and Home; one, two or four panes, each with its own camera; the draw styles
  shaded, flat, x-ray, wireframe and paper.
- **Drive it by text**: every button and key issues a command that the console shows and accepts
  (`view top`, `panes 4`, `style paper`, `load void`, `select tower 3`, `seek 4.2`, `undo`).
- **Use it without a window**: `cav doctor` (adapters, the device, a render self-test), `cav render
  <scene> --view top --out plan.png`, `cav scenes`, `cav schema`, `cav exec "<command>; …"`.
- **Let an agent in**: `cav mcp` answers `scene_schema`, and also `scene_load`, `scene_get`, `command`,
  `log` and `render_view` (a PNG).
- **Load the first dev scenes** from `scenes/dev/`: `void` (the array and nothing else) and
  `infinite-floor` (the array over a floor drawn as a grid to the horizon; no physics yet).
- **Run the tiers**: `cargo xtask quick | gpu | oracle | demo S0 | validate --report`.

## 2. Design in one page

| Crate | Holds in S0 | Depends on |
|---|---|---|
| `cav-core` | `Vec3`, `Mat4` (`f64`); the AION-10 and array defaults | — |
| `cav-sim` | `SceneSpec` (array, instrument, room, floor), RON and JSON forms, its JSON Schema, the built-in scene library and the dev scenes; `ViewSpec` (camera, projection, style, framing) and `Target`, since saved views and selections belong to scenes | `cav-core` |
| `cav-engine` | `Engine`: `Command`, `Query`, the journal (replay), the event log, undo and redo, the view state, the console's text form of every command | `cav-sim` |
| `cav-gpu` | wgpu instance, adapter and device; adapter report; texture read-back | — |
| `cav-render` | cameras, pane layout, scene → drawables (CPU), the wgpu passes that draw a view into a texture, PNG encoding | `cav-core`, `cav-sim`, `cav-gpu` |
| `cav-app` | the egui shell; a headless mode that renders the whole UI to a PNG | `cav-engine`, `cav-render` |
| `cav` | the CLI and the MCP server | `cav-engine`, `cav-render` |
| `cav-validate` | validation cases for tests (TASK-S0-11); no dependencies | — |
| `xtask` | the tiers, the test-count floors, the demo, the validation report; no dependencies | — |

- **One path.** The app, the console, the CLI and MCP all call `Engine::apply(Command)` and
  `Engine::query(Query)`. The console's text is parsed into the same `Command` values; nothing edits
  engine state another way. Every applied command is appended to a journal; replaying a journal on a
  fresh engine reproduces the state exactly (`Engine::digest`).
- **Panes are textures** (research note §1): `cav-render` draws a `ViewSpec` into a texture view it is
  given; the app shows the texture as an egui image; `cav render` and MCP `render_view` read it back
  and encode a PNG. Same function, with and without a window.
- **Frames, not wider floats** (REBUILD §3.4): geometry is built in `f64` and handed to the GPU as
  `f32` offsets from the camera's target.
- **Screenshots never open a window.** `cav-app --screenshot` runs the same UI code against an offscreen
  egui renderer.

### What the tests found

- Pane layout with a gap put an empty pane outside a figure smaller than the gap.
- The menu bar's status text was pushed 6 px off the window.
- The outliner spilled over the timeline in a 1024 × 700 window (it scrolls now).
- Panes were shown too dark: egui treats texture bytes as already sRGB-encoded (`PaneTarget::encoded_view`).
- In a narrow pane a framed plan view was cut off at the sides (the field of view now grows taller instead).
- Two tests of mine had wrong geometry (one tower hiding another; a camera too close after a change of
  projection) and one had a wrong expectation (the framing margin in perspective, and exact equality
  where egui dithers by half a level). In each case the cause was found first and the criterion then
  stated correctly; no tolerance was loosened to pass.

### Better than asked

- A render self-test in `cav doctor` that checks pixels against the f64 camera, not only that a device exists.
- `cav exec` and the MCP `command` tool: the whole console, scriptable; `cav render --exec`.
- MCP beyond `scene_schema`: `scene_load`, `scene_get`, `command`, `log`, `render_view`.
- Framing fits the scene's bounding box for the view's own direction and projection, in any pane shape.
- An unchanged frame redraws no pane.
- Runs of scrubbing and orbiting are one journal entry, so a session's journal stays short and still replays.
- The infinite floor is a per-pixel grid with no vertices to run out of and no large coordinates.
- The log shows each command as the console line that issues it, so a log can be pasted back in.
- Refused commands say what was expected and what exists instead ("it has: instrument, towers").
- The validation report (§8).

### After the review (TASK-S0-12, 13, 14)

A fresh reviewer found one important fault and nine minor ones; all ten are fixed, each with a test that
has a control arm.

1. **A valid spec could hang the renderer, exhaust memory and leave an MCP client waiting.** The spec is
   now bounded (`cav_sim::spec::limits`, stated in the schema); grid lines, ticks, shots and ruler marks
   are counted by whole index with caps, and what is thinned is said (a header badge, a note from
   `cav render`, the timeline's caption); `Renderer::draw` checks buffer sizes and runs in a wgpu error
   scope, returning an error; MCP tools run under `catch_unwind`; nextest kills a test at two minutes.
   No test runs an unbounded case: they use the spec's own limits with the fix in place.
2. `validate` holds case names and tolerances to the committed `report.json` (`--against <revision>`
   for another baseline); a dropped case or a changed tolerance fails unless `acknowledged.txt` gives
   the reason, which the report prints.
3. The projection test holds a distance to 2 px (it used a box whose corners were 2.8 px away).
4. X-ray is tested as additive with depth off. 5. Shading is tested against the light.
6. Scene paths with spaces: the console takes quotes; `cav render` and MCP `scene_load` send the
   `Load` command itself. The log no longer prints a `load` line that would load a different scene.
7. A named view frames the scene, and a framed view stays framed when the projection changes.
8. A console answer is one log entry; `log` is not echoed into the log.
9. The plots say "exact" only where the tolerance is zero.
10. `Engine::frame(pane)` is the one description of what a pane shows; the app, `cav render` and MCP

## 8. The validation report (TASK-S0-11, added by the owner on 21 Nov 2026)

`cargo xtask validate --report` runs every validation case that exists and writes `docs/validation/`:
`report.md` (a table per subsystem, worst margin first), `report.json`, and plots as SVG in light and
dark. How it works, and its rules, are in `docs/validation/README.md`.

| # | Requirement | Tests | Tolerance |
|---|---|---|---|
| V1 | A case records its name, what it is checked against, the measured error, the tolerance, the unit and pass or fail; a convergence case also its measured order against the expected one | `cav-validate`: `a_case_passes_within_tolerance_and_fails_beyond_it`, `convergence_is_judged_by_its_order_as_well_as_its_error`, `records_carry_every_field_on_its_own_line`, `a_failing_case_fails_its_test` | exact; order fit 1e-12 |
| V2 | Cases are declared beside their tests and collected by reading the source: adding a `case!` adds a row | `xtask`: `the_scan_finds_declarations_and_only_declarations` | exact |

| V4 | A case registered twice, without a tolerance, with a test the filter would not run, or recorded but not declared is an error; a tolerance that cannot fail fails | `xtask`: `a_collection_that_cannot_be_trusted_is_an_error`; `cav-validate`: `a_case_without_a_usable_tolerance_fails`, `names_are_checked` | exact |

**Choices.**
- *One axis for the plots:* the margin (measured error over tolerance), log scale, because the cases'
  units differ and a pass is then the same place for all of them. Exact cases have their own column.

  grid. The workflow still commits nothing to `main`. (The alternative, a README line regenerated by
  `validate --report`, would go stale between slices.)
