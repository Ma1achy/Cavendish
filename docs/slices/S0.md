## 1. What the owner can newly do

- **Open the app** (`cargo run -p cav-app`) and see the room and the five towers in a 3-D view, with the
  menu bar, the outliner, the properties panel, the per-tower timeline, the console and the footer.
- **Look around**: orbit, pan and zoom; perspective or orthographic; the named views (iso, top, bottom,
  north, south, east, west) and Home; one, two or four panes, each with its own camera; the draw styles
  shaded, flat, x-ray, wireframe and paper.
- **Drive it by text**: every button and key issues a command that the console shows and accepts
  (`view top`, `panes 4`, `style paper`, `load void`, `select tower 3`, `seek 4.2`, `undo`).
- **Use it without a window**: `cav doctor` (adapters, the device, a render self-test), `cav render
  <scene> --view top --out plan.png`, `cav scenes`, `cav schema`, `cav exec "<command>; …"`.
- **Let an agent in**: `cav mcp` answers `scene_schema`, and also `scene_load`, `scene_get`, `command`,
  `log` and `render_view` (a PNG).
- **Load the first dev scenes** from `scenes/dev/`: `void` (the array and nothing else) and
  `infinite-floor` (the array over a floor drawn as a grid to the horizon; no physics yet).
- **Run the tiers**: `cargo xtask quick | gpu | oracle | demo S0`.

## 2. Design in one page

| Crate | Holds in S0 | Depends on |
|---|---|---|
| `cav-core` | `Vec3`, `Mat4` (`f64`); the AION-10 and array defaults | — |
| `cav-sim` | `SceneSpec` (array, instrument, room, floor), RON and JSON forms, its JSON Schema, the built-in scene library; `ViewSpec` (camera, projection, style), since saved views belong to scenes | `cav-core` |
| `cav-engine` | `Engine`: `Command`, `Query`, the journal (replay), the event log, undo and redo, the view state, the console's text form of every command | `cav-sim` |
| `cav-gpu` | wgpu instance, adapter and device; adapter report; texture read-back | — |
| `cav-render` | cameras and named views, pane layout, scene → drawables (CPU), the wgpu passes that draw a view into a texture, PNG encoding | `cav-core`, `cav-sim`, `cav-gpu` |
| `cav-app` | the egui shell; a headless mode that renders the whole UI to a PNG | `cav-engine`, `cav-render` |
| `cav` | the CLI and the MCP server | `cav-engine`, `cav-render` |
| `xtask` | the tiers, the test-count floors, the demo; no dependencies | — |

- **One path.** The app, the console, the CLI and MCP all call `Engine::apply(Command)` and
  `Engine::query(Query)`. The console's text is parsed into the same `Command` values; nothing edits
  engine state another way. Every applied command is appended to a journal; replaying a journal on a
  fresh engine reproduces the state exactly (`Engine::digest`).
- **Panes are textures** (research note §1): `cav-render` draws a `ViewSpec` into a texture view it is
  given; the app shows the texture as an egui image; `cav render` and MCP `render_view` read it back
  and encode a PNG. Same function, with and without a window.
- **Frames, not wider floats** (REBUILD §3.4): geometry is built in `f64` and handed to the GPU as
  `f32` offsets from the camera's target.
- **Screenshots never open a window.** `cav-app --screenshot` runs the same UI code against an offscreen
  egui renderer.

## 3. Requirements, traced to tests

Every guarding test has a control arm: a case in the same test that breaks the property and must be
seen to fail. Tests whose names contain `gpu_` are the GPU tier; the rest are `quick`.

| # | Requirement | Tests | Tolerance |
|---|---|---|---|
| R1 | The tiers exist; a tier that runs fewer tests than its recorded floor fails | `xtask`: `nextest_summary_gives_the_number_of_tests_run`, `fewer_tests_than_the_floor_fails_the_tier`, `floors_file_is_read_per_tier_and_a_missing_tier_is_an_error`, `the_committed_floors_file_names_both_tiers` | exact |
| R2 | The defaults are the plan's: AION-10 (10 m, Δr 5 m, 2T 1.46 s, cycle 2 s) and five towers on a 4 m cross in a 10 × 10 × 3 m room | `cav-core`: `default_array_is_five_towers_in_a_cross_inside_the_room`, `instrument_defaults_are_the_aion_10_preset` | exact |
| R3 | Camera maths is right-handed, z up, wgpu clip space | `cav-core`: `cross_product_is_right_handed`, `look_at_puts_the_target_on_the_axis_ahead`, `perspective_maps_near_and_far_to_depth_zero_and_one`, `perspective_shrinks_with_distance_and_orthographic_does_not`, `matrix_product_applies_the_right_factor_first` | 1e-12 |

## 4. Demo script

`cargo xtask demo S0` runs, with no window:

1. `cav doctor` → `docs/slices/S0/doctor.txt`.
2. `cav render` of the room, `void` and `infinite-floor` in several views, projections and styles → PNGs.
3. `cav-app --screenshot` of the whole UI: the default layout, four panes, paper style, the console
   open, F3 → PNGs.
4. An MCP session against `cav mcp` (initialize, `tools/list`, `scene_schema`, `render_view`) →
   `mcp-session.txt` and a PNG.
5. Frame-time measurements → `timings.txt`.

By hand, in the app: drag to orbit, scroll to zoom, press `O`, `1`–`5`, `Home`, `F3`, `` ` ``; type
`panes 4`, `style paper`, `load void`, `undo` in the console.

## 6. Where the plan and the reference disagree (the plan wins)

- `reference/milestones/M13` §9 names crates and modules of v1 (`viewer`, `generate`); the layout here
  is REBUILD §3.1's.
- M13 §9.2 docks panels with `egui_dock`; S0 uses fixed egui panels (no docking dependency until a
  slice needs saved layouts).
- `reference/design/instrument.md` uses δφ₂ − δφ₁, ⁸⁸Sr's mass and (in v1's code) no floor; George's
  answers of 21 Nov 2026 (`plan/PROGRESS.md`) change all three from S1 on. S0 draws no flight and
  computes no phase, so nothing here depends on them.
