## 1. What the owner can newly do

- **Keep scenes as files.** `save my-scene.ron` writes the scene; `load my-scene.ron` reads it;
  `cav get|set|ls|schema <scene> [path]` read and edit a file from the command line.
- **Edit anything from anywhere, one way.** The properties panel has an editor for every field,
  made from the schema (unit, range and the doc string as hover text). A panel, the console
  (`set`, `add`, `remove`), `cav set`, and an agent over MCP (`scene_set`, `scene_ls`, an inline
  spec to `scene_load`) all issue the same commands. Undo and redo take back any of them.
- **Replay a session.** `journal save session.json`, then `cav replay session.json --out dir/`
  re-runs it and writes the same files, byte for byte.
- **Give each tower its own clock.** `array.towers[n].timing.offset`; the timeline has one lane
  per tower and a lane can be dragged sideways to set the offset; `show flight` draws the atoms'
  space–time diagrams of every tower on one absolute time axis.
- **Switch instrument.** `preset aice` or `preset aion10` (or a file of your own); `compare aice`
  draws every plot a second time for the same scene on the other instrument.
- **Design a cadence.** Cycle jitter (symmetric or positive only; a random walk or about a grid),
  alternation, planned gaps, a loss probability and a daily window live in `array.schedule`;
  `show cadence` draws the spectral window with the predicted alias lines, floors and the loss of
  sensitivity, live, as the fields are edited. Uneven sampling is read with the NUFFT
  Lomb–Scargle.
- **Run headless and get a bundle.** `cav run scene.ron --out dir/` writes `.npy` arrays named
  and shaped as v1's `StateBundle`, each tower's own readout times, the numerics block and the
  per-tower error estimate.
- **Export figures.** `figure periodogram --preset paper-column --out fig.pdf` (also `.svg`,
  `.png`) from the console, `cav figure …` and MCP: the figure, the data behind it (`.csv` or
  `.npy`) and a JSON of axes, units and provenance. `python/cavendish_figures` redraws one from
  its data with matplotlib in the same house style.
- **Find your way round the code.** `docs/ARCHITECTURE.md`, `CONTRIBUTING.md` and a recipe in
  `docs/extending/` for each kind of thing that can be added.

### One edit path

```
editor / drag / console line / cav set / MCP scene_set / a loaded file
        └──► Command::{Set, Insert, Remove, Load, Undo, Redo, …} ──► Engine::apply
                 │ check (paths in cav-sim, then SceneSpec::validate)      │ journal (the replay)
                 │ history: the inverse edit, by bytes, oldest dropped     │ log: the console line
                 └──► forward workers (stale, then refined) ──► Query / Export
```

- **Paths** (`cav_sim::paths`): the note's option A, finished. A path is parsed once into
  segments (`array.towers[2].timing.offset`, an enum through its variant:
  `bodies[0].motion.Static.position`); `get`, `set`, `insert`, `remove`, `ls` and `schema_at` walk
  a `serde_json::Value` of the spec and its JSON Schema. Units (`x-unit`) and the stage an edit
  invalidates (`x-stage`) are `schemars` attributes on the fields; `diff(a, b)` names the earliest
  stage. The engine, `cav get|set|ls`, MCP and the editors all call this one module.
- **Undo** is an inverse edit per step (a few bytes for a `Set`), with whole scenes kept only for
  `Load`. The history is bounded by bytes (§3.1).
- **Export** is a command, so a session's journal says what it wrote. Replaying a journal never
  writes to the paths in it: the replayer names a directory and exports land inside it, or are
  skipped. A relative path keeps its folders under the directory; an absolute one, or one with
  `..` in it, keeps its file name alone; two different paths that would land on one file are
  kept apart (`name (2).ext`), and the log says so (§7.12). Bundles, scenes and journals are
  written by the engine; figures by an exporter the client installs (`cav-plot`), since the
  engine does not draw.
- **The journal is counted in the bytes its file takes** and stops at 64 MiB, the most a journal
  file may be read at. Past that the session goes on, unrecorded; `journal restart` starts a new
  journal from the session as it stands (§7.12).
- **Non-finite numbers in JSON.** Replies carry floats through `cav_sim::json_f64`: finite values
  as numbers, `±∞` as the strings `"inf"` and `"-inf"`, NaN as `"nan"` (its bits are not kept, and
  no bundle may hold one). A half-space's single-interferometer channels now survive MCP.

### Per-tower time

`TowerSpec.timing.offset` (seconds, default 0) shifts every shot of that tower. `ArraySpec.schedule`
is the array's clock: when shot `k` is launched, and which shots are not taken. Tower `d` reads
shot `k` out at `launch_k + offset_d + 2T`. All towers take the same number of shots, so the
arrays stay rectangular `(T, D)`; a shot not taken (a planned gap, the daily window, a lost shot)
is a slot whose `valid` flag is false and whose value is 0, never NaN. With no offsets and the
uniform schedule every number is the bits S1 produced (`zero_offsets_are_the_old_schedule`).

### Cadence (`cav_core::cadence`, `cav_sim::schedule`)

Random numbers are a keyed hash of `(seed, stream, tower, shot)` (SplitMix64), never a stream
with state, so thread count and order cannot matter. The designer draws the *expected* spectral
window from closed forms (uniform, cycle jitter as a random walk, jitter about a grid, alternation,
planned gaps, loss) and one *realisation* for the scene's seed by direct sum (short runs) or NUFFT.

### The bundle (`cav_sim::bundle`)

```
dir/manifest.json      names, shapes, dtypes; the numerics block; the scene, verbatim; the sign note
dir/scene.ron          the scene as saved
dir/time.npy               (T,)      f8  each shot's readout on the array's clock, seconds
dir/detector_time.npy      (T, D)    f8  each tower's own readout time, seconds
dir/valid.npy              (T, D)    b1  whether the shot was taken
dir/signal.npy             (T, D)    f8  ΔΦ, radians; lower minus upper unless the scene says otherwise
dir/signal_per_ifo.npy     (T, D, 2) f8  δφ₁ (lower), δφ₂ (upper), radians
dir/detector_placement.npy (D, 7)    f8  x, y, z of the base, then the quaternion w, x, y, z
dir/source_position.npy    (S, T, 3) f8  each body's position at `time`, metres
dir/source_mass.npy        (S,)      f8  kilograms
dir/error_estimate.npy     (D,)      f8  the largest quadrature estimate of any shot, radians
```

Names and shapes are v1's (`design/state.md` at `v1-final`), measurement first. Everything is f64:
the engine is f64 on the CPU until S5. The manifest says `sign: lower minus upper (δφ₁ − δφ₂);
v1 bundles are upper minus lower`. A bundle is written only from a refined signal; a NaN anywhere
is refused with its place. Arrays are written through a buffer, so writing costs no second copy.

The numerics block names the engine that made the bundle: its version, the `revision` it was
built from and whether its sources were then `dirty` (`true`, `false` or `"unknown"`), with a
sentence saying what the two are. They are the build's: a build script asks git once, when the
engine is compiled, and nothing is asked when a file is written (§7.12). A bundle is of the
scene's own instrument; written while a comparison is on, its manifest and the log say that the
comparison's reading is not in it.

### Figures (`cav-plot`)

A plot is built once as a display list in points (1/72 inch): lines, rectangles, circles, text.
The application paints the list with egui; SVG and PDF are that list written out, with text as
glyph outlines read from the two fonts already in the binary (Ubuntu Light and Ubuntu Mono, with
`skrifa`, which egui already compiles), so a figure looks the same wherever it is opened and the
PDF needs no font machinery; PNG is the list painted by egui's renderer at the stated resolution.
The PDF writer is in-house (one page, one uncompressed content stream; no dependency). A view of
the 3-D scene is exported as PNG, or as an SVG/PDF holding that picture; vector drawings of the
scene are S4's paper style. Presets: `paper-column` (85 mm), `paper-full` (178 mm), `slide`
(254 × 143 mm), `poster` (400 mm), `screen` (the application's dark theme); `paper` periodograms
are the house style of VALIDATION §3 item 8 (log y, grey floors at 1e-4 and 1e-5 rad/√Hz, stems
for the comb, a diamond at the ULDM benchmark).

### 3.3 Criteria written before measuring

- **R3.** The note measured 0 of 10⁷ through JSON with `float_roundtrip` and through RON. Expected
  here: 0 of 10⁶ each, through the typed struct and through `serde_json::Value`.
- **R7.** Each shot's value depends only on the scene and its own readout time; nothing is summed
  across threads; the sum over sources is in the scene's order. Expected: 0 bytes differing in
  every arm. The claim is **same binary, same platform, CPU path** (the note, §2.4: `sin` and
  `cos` are the platform's).
- **R8.** A tower's readout is `launch + offset + 2T`; with offset 0.0 that is the same addition
  as S1's `launch + 2T`, so the bits are S1's. With an offset δ the tower's shot is read at a time
  that differs from "the synchronous scene at t + δ" by at most one rounding of the time (2e-16 of
  it), so the phases agree to 1e-12 of the peak with three decades in hand.
- **R13, each against the note's closed form:**
  - *uniform*: `|W|` is the Dirichlet kernel, to 1e-12 (the note: 1e-14).
  - *alternating* `T_A, T_B`: sidebands at `k/T_s` of relative height `|cos(π k T_A / T_s)|`,
    to 1e-3 at N = 2000 and equal at N and 10 N to 1e-3. Control: with cycle jitter in place of
    alternation the height at N and 10 N differs by more than 30%.
  - *planned gaps*, L of every P: lines at `k/(P T₀)` of height `|sin(πkL/P) / (L sin(πk/P))|`,
    to 1e-9 for a whole number of periods.
  - *cycle jitter* (random walk), positive and symmetric, δ = 0.1 and 0.3 s at T₀ = 5 s, N = 500:
    the mean of `|W|²` over 2000 keyed seeds at the alias `1/T̄` and at two frequencies off it is
    the closed form to within 3 standard errors of that mean (the standard error measured from the
    seeds) and within 8%.
  - *jitter about a grid*: `E|W|² = |ψ|²|D_N|² + (1 − |ψ|²)/N` at the first alias, the same
    criterion; and the line's height at N and 10 N equal to 3% (it does not recede).
  - *loss*: the floor `p/((1 − p)N)` for p = 0.01 and 0.05 at N = 4000, away from the lines: the
    mean over 400 seeds and 64 frequencies within 5% (the note saw 6% and 1.4% with 300 seeds and
    could not say whether the 6% was noise; if it is not, this fails and is explained, not moved).
  - *alias ratio against N*: the predicted `√E|W|²` at `1/T̄` falls with a local slope between
    −0.40 and −0.50 from N = 5×10³ to 10⁵ for δ = 0.1 and 0.3 s, and equals the note's 0.660,
    0.382, 0.263 (N = 5×10³) and 0.175, 0.089, 0.060 (10⁵) to three figures.
- **R14.** S1 measured the NUFFT Lomb–Scargle at 3e-15 of the peak against the exact one;
  through the engine, on a jittered and gapped series of a comb scene: ≤ 1e-9.
- **R17, the palette.** Written before the `dataviz` validator was run: every pair of the eight
  series colours differs by ΔE ≥ 12 (CIEDE2000 or the skill's own measure) in normal vision and
  under simulated protanopia, deuteranopia and tritanopia; the first four also differ in lightness
  by at least 8 L* from each other so that they survive grey print.
- **`quick` after a rebuild.** Measured first, in §7.2, before anything is changed for it.

### 7.11 After the review: shots drawn as scheduled

TASK-S2-14, for two important findings of the fresh review of the slice (I1: the lanes and the
flight diagram drew `k·cycle`, all taken, whatever the schedule; I2: a shot not taken was drawn as
a measurement of 0 rad, joined into the line) and four minor ones (14, 21, 22 and the shots' part
of 29). Rules and criteria were written here before anything was measured; what was measured
follows them.

**One source.** `cav_sim::read::shots(spec)` makes a scene's `Shots` (each shot's readout on the
array's clock, each tower's offset, which shots each tower takes, 2T, and the schedule's
warnings). The engine makes them once an edit, where it always did (to plan the read), and keeps
them: `Engine::shots()`. The read, the lanes, the flight diagram and its data table go by those;
the signal plot, its data table and the Python redraw go by the signal's own copy of the same
flags (`Signal::valid`: a stale signal is drawn with the shots it was read at); every caption that
counts shots goes by `Query::Cadence`, which counts them from `read::shots` and is now kept
between frames. Nothing that draws computes a shot time from `k·cycle`.

**The rule for a launch before zero, and for offsets (finding 22).**

1. The array's clock launches nothing before t = 0: the clock starts at zero. Jitter that only
   delays, a random walk and alternation never did. Symmetric jitter about a grid did (shot 0
   drawn early), so there the grid now stands δ after zero: shot `k` is launched at
   `k·cycle + δ + δ(2u − 1)`, in `[k·cycle, k·cycle + 2δ)`. Every shot moves alike, so no height
   of the spectral window changes; the generator `cav_core::cadence::grid_times`, which the
   closed forms were checked against, is untouched, and a scene's launches are its times plus δ
   to the bit. Chosen over skipping the early shot (half of all seeds would lose shot 0 for no
   physical reason) and over refusing it.
2. A shot is the timeline's when its place on the grid is before the end, as in S1; its launch
   may be later than the end by its jitter and its readout by 2T more.
3. A tower's offset moves that tower's shots and changes nothing else (R8 stays exact, and a
   lane can be dragged either way). An offset that puts a launch before 0, or at or after the end
   a shot the array's clock launches before it, is said: a warning about that tower, with the
   count and the time, in the shots, in the signal read from them, and so in the log, in
   `signal`'s answer and in the bundle's manifest. The shots stay taken: marking them not taken
   would make an offset change values, which R8 forbids.

No validation case uses symmetric jitter about a grid through `read::launches`, and none has an
offset that reaches outside the timeline, so no case's measured value should change: checked
against the report at `s1-point-mass` below.

**Finding 21.** `Prediction::noise_factor` and `::floor` are absent rather than wrong: the factor
when a tower takes no shot (it was infinite, printed as a number), the floor when loss leaves a
tower fewer than 20 shots expected. The loss floor `p/((1 − p)N)` is the first term of

form is good to about one part in the shots expected to be kept: 5% at 20, which is the tolerance
it was held to in §3.3. Below that the answer says so in words and gives the regime.

longer computes a prediction at all (it wanted only the mean cycle).

### 7.12 After the review: provenance is the build's; replay and journal

#### The fault (I3)

`cav_engine::build()` ran `git rev-parse HEAD` and `git status --porcelain` in the source tree
the first time it was called, and the answer went into every manifest and every figure's
`.json`. So the same binary wrote other bytes once the tree had moved (the reviewer: one
untracked file between two replays, 13 files differ), and a binary run after the tree had moved
recorded a revision and a flag it was not built from. The manifest's own line, "bit-identical
with the same binary on the same platform", was false. Departure 5 of §7.9 is withdrawn.

#### What is done

A build script in `cav-engine` (`build.rs`; its decision is `provenance.rs`, included by the
script and by a unit test) asks git once, when the engine is compiled, and hands the answers to
the compiler (`cargo:rustc-env`). `cav_engine::build()` reads two compiled-in strings and runs
nothing. No dependency was added.

- **`revision`**: the commit that was checked out when the engine was compiled: the answer to
  `git rev-parse --show-prefix HEAD` asked in the workspace root, taken only if that root is
  the top of a work tree (a workspace that is a folder of someone else's repository would
  otherwise carry their commit) and only if it is a commit's name.
- **`dirty`**: `true`, `false` or `"unknown"`: whether **the engine's sources** then differed
  from that commit, by `git status --porcelain` held to them: a tracked file changed, staged or
  not, or a file git neither tracks nor ignores. The engine's sources are what makes the
  numbers: `crates/cav-core`, `crates/cav-sim` and `crates/cav-engine` (each one's `src` and
  `Cargo.toml`; the engine's `build.rs` and `provenance.rs`), `scenes/` (built into the
  library), the workspace's `Cargo.toml` and `Cargo.lock`, `rust-toolchain.toml` and `.cargo/`.
  **It says nothing of `cav-plot`, `cav-render`, `cav-gpu`, `cav-app` or `cav`**: a figure
  drawn by an edited `cav-plot` on a clean engine says `dirty: false`. Those crates are at the
  same revision. This is the narrower of the two definitions the task allowed, chosen for its
  cost (below), and it is written into every file: `engine.built_from` says in a sentence what
  the two are and that git is not asked when the file is written.
- **Built outside git** (no git on the PATH, no repository, no commit yet, or a workspace
  inside another repository): both are `unknown` and the build goes on.
- **When the stamp is made again.** Cargo runs the script again when one of those sources
  changes, or `.gitignore`, or what in git moves with the commit and the set of tracked files:
  `HEAD`, its log, the branch it names, the packed refs and the index (found with
  `git rev-parse --git-path`, so a linked work tree is right too). Git is asked with
  `--no-optional-locks`, so asking does not rewrite the index it watches. Not seen, and said:
  an untracked source file *deleted* (the flag stays `true` until something else runs the
  script); a file put back with an old modification time (which the compiler does not see
  either).

#### The criteria, written first

**10, a figure is bounded in series.** A signal plot (the pane's and the figure's: one function)
draws at most `plots::MAX_SERIES` = 12 towers' lines. With more towers than that and none named,
the first twelve are drawn, except that a selected tower outside them takes the twelfth place;
the plot says so under the axes at every size ("12 of 1000 towers drawn", and which while there
is room) and the figure's `.json` lists which. The data file still holds every tower, and is
written a row at a time through a 64 KiB buffer from the engine's own signal: no table of it is
ever built. Data is text (`.csv`) only up to 20,000 rows and 300,000 values (what the row rule
alone allowed the five-tower scenes); beyond either it is `.npy`. For 1000 towers × 4000 shots,
measured with the counting allocator around the whole export of an SVG: **at most 16 MiB live
beyond the engine's own signal** (chosen from what the drawing needs: twelve series of 2000
points, the scene of a thousand towers twice as JSON, three thousand column names; then
measured), **the SVG under 2 MB**, the time recorded and not gated. Controls, measured in the
same test: the same plot with the cap lifted holds more points than 2 MB of SVG can; the table
held in memory is more than the bound by itself.

**13, MCP's pixel limit.** The `figure` tool refuses a picture (a PNG, or a view in any format)
with a side over 4096 pixels, with the numbers, before anything is drawn; 4096 is drawn; the
command line and the console still take 8192 and refuse 8193. A vector plot has no pixels and is
not refused.

**26, one record for a figure's files.** `fig.json` is the record of the figure `fig`: one set
of data (what is plotted, of which tower, channel, span and pane, from which scene, build and
numerics, in which data file) and, under `files`, every picture written of it, each with what is
its own (format, preset, size, pixels and resolution, title, axes, series, marks, colours, the
command). The layout's version becomes 2. The rule:

1. Writing `fig.pdf` when `fig.json` records the same data adds `fig.pdf` to `files`, or
   replaces its entry; the entries are in the order of their names. An entry whose file is no
   longer there is dropped.
2. Writing it when `fig.json` records other data (another scene, tower, span, build), or is not
   a record this build reads, replaces the record and the data file with the new figure's. The
   pictures the old record listed that are still there are not this figure: they are named under
   `not_this_figure` until they are written again, and never under `files`.
3. So the record depends on which figures were written and what was in the directory, not on
   the order; the same command twice changes no byte; `figure.regenerates` and
   `figure.png_regenerates` stay at 0.

Test: SVG then PDF then PNG of one stem lists three; in the other order the same bytes; a
second run changes nothing; another tower to the same stem replaces the record and names the
two left behind; writing those again clears the list. Control: the record as it was written
before (the last format's alone) is not the three-file record.

**28, the palette under two simulations.** Every pair of the eight series colours differs by
CIEDE2000 ≥ 12 in normal vision and under protanopia, deuteranopia and tritanopia as simulated
by **both** Machado, Oliveira and Fernandes 2009 (severity 1.0) and Viénot, Brettel and Mollon
1999 (protanopia and deuteranopia; Brettel, Viénot and Mollon 1997 for tritanopia): seven
conditions, 28 pairs each. The first four differ pairwise by at least 8 L*. Each has at least
3:1 contrast on white. The `dataviz` skill's validator passes on white, all pairs. Control: the
palette this replaces, whose blue against purple under Viénot protanopia the reviewer measured
at 10.37, fails the same assertion. If no eight colours meet all of it, the best achievable
minimum and its condition are reported here and the criterion restated with its reason; the
number is not lowered silently.
